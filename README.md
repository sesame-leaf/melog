# melog

ML 실험을 하나씩 정형화된 형태로 기록하는 CLI 도구입니다.

> 구현 설계는 [docs/design.md](docs/design.md), 구현 순서와 진행 상황은 [docs/plan.md](docs/plan.md)에서 다룹니다.

## 설치

git과 [uv](https://docs.astral.sh/uv/)가 필요합니다. Python 3.13 이상이 필요하지만, uv가 알아서 준비합니다.

```bash
# 저장소를 clone해 둔 경우
uv tool install /path/to/melog

# GitHub에서 바로 설치하는 경우
uv tool install git+https://github.com/sesame-leaf/melog
```

설치하면 어느 디렉터리에서나 `melog` 명령을 쓸 수 있습니다. melog는 실험을 진행하는 저장소와 별개로 설치되므로, 실험 저장소가 uv를 쓰지 않아도 됩니다.

## 빠른 시작

실험을 진행하는 git 저장소 안에서 다음과 같이 씁니다.

```bash
# 1. melog 프로젝트를 만듭니다 (모델마다 하나씩 만들 수 있습니다)
melog init lgbm

# 2. 실험을 시작합니다. 이 시점의 코드가 시작 스냅샷으로 남습니다
melog start "LightGBM baseline" --motivation "Discussion에서 본 설정으로 시작" --entry train.py

# 3. 평소처럼 코드를 고치고 실행합니다. 커밋할지는 자유입니다

# 4. 실험을 끝냅니다. 이 시점의 코드가 종료 스냅샷으로 남습니다
melog done --score CV=0.812 --score "CV std=0.004" --verdict "베이스라인으로 쓸 만함"

# 5. 무엇이 바뀌었는지 확인하고, 실험 기록의 본문을 채웁니다
melog diff bjs-1
melog edit bjs-1

# 6. 지금까지의 실험을 봅니다
melog list
melog lineage

# 7. 대회가 끝나면, 보고서의 재료를 한 문서로 모읍니다
melog export -o experiments.md
```

처음 `melog start`를 실행하면 실험 id에 쓸 이니셜(예: `bjs`)을 묻습니다. 미리 정해 두려면 `git config --global melog.initials bjs`를 실행합니다.

터미널에서 실행하면, 옵션으로 주지 않은 값(제목, 동기, 점수, 판정)을 차례로 묻습니다. 모든 질문은 Enter로 건너뛸 수 있습니다.

## 명령어

| 명령어 | 하는 일 |
|---|---|
| `melog init <이름>` | melog 프로젝트를 만듭니다 |
| `melog project edit` | 옵션 없이 실행하면 프로젝트 개요를 에디터로 열고, `--scores`나 `--horizontal`을 주면 설정을 바꿉니다 |
| `melog start [제목]` | 실험을 시작합니다 |
| `melog done [ID]` | 실험을 끝냅니다. `--new <제목>`을 주면, 시작을 선언하지 않고 진행한 실험을 사후 등록합니다 |
| `melog abandon [ID]` | 실험을 중단합니다. 중단한 실험도 기록으로 남습니다 |
| `melog import <프로젝트>/<id>` | 다른 melog 프로젝트의 실험을 가져옵니다 |
| `melog edit [ID]` | 옵션 없이 실행하면 실험 기록을 에디터로 열고, 옵션을 주면 지정한 항목만 고칩니다 |
| `melog show ID` | 실험 기록 하나를 보여 줍니다 |
| `melog list` | 실험 목록을 보여 줍니다 |
| `melog lineage` | 실험의 계보를 트리로 보여 줍니다. `--mermaid`를 주면 mermaid 그래프로 출력합니다 |
| `melog export` | 프로젝트의 개요, 계보, 실험 기록을 한 Markdown 문서로 모읍니다 |
| `melog diff ID` | 실험에서 바뀐 코드를 보여 줍니다. 노트북은 코드 셀만 비교합니다 |
| `melog checkout ID [경로]` | 실험의 코드를 별도의 디렉터리(git worktree)에 꺼냅니다. 그 디렉터리에서 바로 새 실험을 시작할 수 있습니다 |
| `melog sync` | 원격 저장소를 통해 실험 기록과 코드 스냅샷을 팀원과 공유합니다 |

각 명령의 인자, 옵션, 동작, 출력 형식은 [docs/commands.md](docs/commands.md)에 정리되어 있고, `melog <명령어> --help`로도 볼 수 있습니다. `done`, `abandon`, `edit`에서 ID를 생략하면, 이 작업 공간에서 진행 중인 실험을 대상으로 삼습니다.

## 에이전트에서 쓰기

melog는 사람과 에이전트가 같은 명령을 씁니다.

- 모든 명령에 `--json`을 주면 기계가 읽을 수 있는 JSON을 출력합니다.
- 터미널이 아니거나 `--json`을 주면 아무것도 묻지 않습니다. 필요한 값은 옵션으로 줍니다.
- 본문은 `melog edit bjs-3 --changes - < summary.md`처럼 표준 입력으로 채울 수 있습니다.
- 동기화할 때 충돌이 나면 아무것도 바꾸지 않고 종료합니다. `--prefer local` 또는 `--prefer remote`로 해결할 수 있습니다.

## 알아 둘 점

- **스냅샷에는 커밋하지 않은 파일도 들어갑니다.** git이 무시하지 않는 파일은 모두 스냅샷에 들어가고, `melog sync`를 실행하면 원격 저장소에도 올라갑니다. 데이터, 모델 가중치, 비밀 정보(`.env` 등)는 `.gitignore`에 넣어 두세요. 처음 동기화할 때는 올라갈 파일 목록을 보여 주고 확인을 받습니다.
- **사용자의 브랜치와 커밋 이력은 바뀌지 않습니다.** melog는 실험 기록과 스냅샷을 전용 참조(`refs/melog/...`)에 저장합니다. 그래서 평소의 `git log`, `git push`에는 나타나지 않습니다. 다만 모든 참조를 보여 주는 `git log --all`에는 melog의 커밋도 함께 나타납니다.
- **병렬로 실험하려면 작업 공간을 나눕니다.** 하나의 작업 공간에서는 진행 중인 실험을 하나만 둘 수 있습니다. `git worktree`로 작업 공간을 나누거나, 실험마다 파일이 분리되는 프로젝트라면 `melog init --horizontal`로 만듭니다.

## 만든 이유

Kaggle이나 Dacon 같은 ML 대회가 끝나면 보고서를 써야 하는 경우가 많습니다. 보고서를 쓰려면 대회를 진행하는 동안 어떤 생각으로 무엇을 시도했는지 되짚어야 하는데, 기록이 남아 있지 않으면 그 과정을 복원하기 어렵습니다.

melog는 이 문제를 해결하기 위해 다음 과정을 거쳐 만들어졌습니다.

1. **hypothesis-driven-ml-workflow**: 에이전트 skill로 실험 과정을 기록하려 했지만, 기록뿐 아니라 작업 방식까지 강제해서 불편했습니다.
2. **ml-experiment-log**: 작업 방식은 강제하지 않고 기록 형식만 정형화한 skill입니다. 기록 절차는 에이전트가 수행했습니다.
3. **melog**: 기록 절차의 대부분은 에이전트에게 맡기지 않아도 자동화할 수 있습니다. 그래서 이 절차를 사람과 에이전트가 모두 쓸 수 있는 CLI 도구로 옮겼습니다.

## 본질

melog는 **실험하는 동안 남긴 기록이 그대로 보고서의 재료가 되게 하는 도구**입니다.

실험마다 실험 기록이 정형화된 형태로 남기 때문에, 사용자는 기록 형식을 미리 고민하지 않아도 나중에 과정을 쉽게 되짚을 수 있습니다.

## 범위

**포함하는 일**

- 실험마다 정형화된 실험 기록을 남기는 일
- 기록된 내용을 보여 주는 일

**제외하는 일**

- 기록을 해석하거나 판단하는 일 (예: 다음 실험 제안, 실험 간 우열 분석)
- 작업 방식이나 작업 순서를 강제하는 일
- 코드 실행, 모델 학습, 데이터 관리

## 원칙

- **melog는 기록의 형식과 절차를 관리하고, 기록의 내용은 사용자가 책임집니다.** 예를 들어 판단의 주체가 누구였는지 남길지, 실행 전에 쓴 동기를 나중에 고칠지는 사용자가 결정합니다.
- **작업 방식을 강제하지 않습니다.** 실제 대회에서는 아이디어의 출처와 실험의 크기가 다양하고, 여러 실험을 병렬로 진행하기도 합니다. 다만 기록의 정확성을 위해 필요한 최소한의 규칙은 둡니다. 예를 들어 하나의 작업 공간에서는 진행 중인 실험을 하나만 둘 수 있습니다.
- **사람이 직접 쓸 수 있어야 하고, 에이전트도 쓸 수 있어야 합니다.**
- **git 저장소를 필수 전제로 합니다.** 코드 스냅샷은 git을 이용해서 남깁니다.

## 핵심 기능

1. **계보(lineage) 보기**: 지금까지의 실험을 한눈에 볼 수 있습니다.
2. **실험 코드 재현**: 저장소의 구조와 상관없이 각 실험의 코드를 보고 재현할 수 있습니다. 실험마다 파일을 새로 만드는 수평 구조, 기존 코드를 수정하면서 커밋하는 수직 구조, 두 방식을 함께 쓰는 구조를 모두 지원합니다. 재현의 대상은 git으로 관리되는 코드에 한정되며, `.gitignore`로 제외된 데이터나 모델 가중치는 포함하지 않습니다.
3. **실험 기록 모아 보기**: 지금까지의 실험 기록을 편리하게 모아 볼 수 있습니다.

## 용어

| 용어 | 영어 | 뜻 |
|---|---|---|
| 실험 | experiment | 한 번의 시도입니다. 대회 전체에 걸친 작업이 아니라, 그 안에서 무언가를 한 번 해 보는 단위를 가리킵니다. 사용자가 시작을 선언하고, 완료나 중단을 선언합니다. 실험의 크기는 사용자가 정합니다. 완료된 실험의 코드를 고쳐서 다시 실행하는 경우는 새 실험으로 기록하고, 기존 실험을 부모로 선언합니다. |
| 실험 기록 | record | 실험 하나에 대해 남기는 정형화된 문서입니다. |
| melog 프로젝트 | melog project | 서로 격리된 실험 집합입니다. 저장소 하나에 여러 melog 프로젝트를 둘 수 있으며(예: 모델별), melog 프로젝트끼리는 서로를 참조하지 않습니다. |
| 코드 스냅샷 | snapshot | 특정 시점의 코드 상태 전체입니다. 실험마다 시작을 선언한 시점의 시작 스냅샷과, 완료나 중단을 선언한 시점의 종료 스냅샷을 남깁니다. 종료 스냅샷이 그 실험의 코드이고, 시작 스냅샷은 변경점을 쓸 때 참고하는 기본 비교 대상입니다. |
| 진입점 | entry point | 종료 스냅샷 안에서 그 실험의 코드를 대표하는 파일입니다. 노트북, Python 스크립트, 설정 파일 등 형식에 제한이 없습니다. 선택적으로 기록하며, 하나의 실험에 여러 개를 기록할 수 있습니다. |
| 작업 공간 | workspace | 실험을 진행하는 코드의 작업 사본 하나입니다. 예를 들어 저장소를 clone한 디렉터리나 git worktree 하나가 작업 공간 하나에 해당합니다. |
| 결과 | result | 실험에서 관찰된 사실입니다. 실험 기록의 본문에 서술합니다. |
| 점수 | score | 실험에서 얻은 점수입니다. 본문과 분리된 항목으로 기록하며, 비워 둘 수 있습니다. melog 프로젝트마다 기본으로 기록할 점수의 목록(점수 구성)을 정할 수 있고, 따로 정하지 않으면 CV, CV 표준편차, public LB를 기록합니다. 점수 구성에 없는 점수도 실험 기록에 추가로 남길 수 있습니다. |
| 판정 | verdict | 실험에 대한 사용자의 판단을 짧게 적은 것입니다. 본문과 분리된 항목으로 기록하며, 비워 둘 수 있습니다. 정해진 선택지 없이 자유롭게 적습니다. |
| 부모 | parent | 같은 melog 프로젝트 안에서, 어떤 실험의 바탕이 된 실험입니다. 사용자가 선언하며, 여러 개를 선언할 수 있고 순서나 우열은 없습니다. 부모가 없는 실험은 새로운 출발점이 됩니다. 부모 관계에는 순환이 있으면 안 됩니다. 부모는 코드의 출처나 변경점의 비교 대상과 별개의 관계입니다. 다른 melog 프로젝트의 실험은 부모가 될 수 없으므로, 먼저 가져오기를 해야 합니다. |
| 가져오기 | import | 다른 melog 프로젝트의 실험을 이 프로젝트의 새 실험으로 만드는 일입니다. 가져온 실험은 이 프로젝트에서 새로운 출발점이 되고, 출처를 기록합니다. 상태는 완료가 되고, 원래 실험의 종료 스냅샷을 이 실험의 종료 스냅샷으로 삼습니다. 원래 실험 기록의 점수와 결과는 복사하지 않습니다. |
| 출처 | origin | 가져온 실험이 원래 어느 melog 프로젝트의 어떤 실험이었는지 나타내는 정보입니다. 원래 프로젝트의 이름, 원래 실험의 id, 원래 실험의 종료 스냅샷을 담습니다. 가져온 시점의 사실을 기록할 뿐이며, melog가 이 정보를 따라 다른 프로젝트를 참조하지는 않습니다. |
| 상태 | status | 실험이 어느 단계까지 진행되었는지 나타내는 값입니다. 진행 중(`in_progress`), 완료(`done`), 중단(`abandoned`) 중 하나이며, melog가 관리합니다. 중단된 실험도 실험 기록으로 남깁니다. 사용자가 실험의 시작을 선언하면 진행 중, 완료를 선언하면 완료, 중단을 선언하면 중단 상태가 됩니다. |
| 보고서 | report | 대회가 끝난 뒤 사용자가 작성하는 최종 문서입니다. melog는 보고서를 다루지 않고, 보고서의 재료가 되는 실험 기록을 남깁니다. |

## 실험 기록의 구성

실험 기록은 다음 항목으로 구성됩니다. 선택 항목은 비워 둘 수 있습니다.

| 분류 | 항목 | 채우는 주체 | 필수 여부 |
|---|---|---|---|
| 식별 | id | melog | 자동 |
| 식별 | 제목 | 사용자 | 필수 |
| 식별 | 시작 시각, 종료 시각 | melog | 자동 |
| 관계 | 부모 | 사용자 | 선택 |
| 관계 | 출처 | melog | 가져온 실험에만 |
| 코드 | 시작 스냅샷, 종료 스냅샷 | melog | 자동 |
| 코드 | 진입점 | 사용자 | 선택 |
| 진행 | 상태 | melog (사용자의 선언에 따라) | 자동 |
| 결과 요약 | 점수 | 사용자 | 선택 |
| 결과 요약 | 판정 | 사용자 | 선택 |
| 본문 | 동기와 예상, 변경점, 결과, 메모 | 사용자 | 선택 |

- **id**는 melog 프로젝트 안에서 고유하며, 여러 사람이 동시에 실험을 시작해도 충돌하지 않아야 합니다.
- **제목**은 실험을 가리키는 짧은 이름입니다. 본문을 비워 두더라도 제목만 있으면 어떤 실험이었는지 떠올릴 수 있도록 필수로 둡니다.
- **시작 시각과 종료 시각**은 사용자가 실험의 시작과 종료(완료나 중단)를 선언한 시각이며, 두 코드 스냅샷을 남긴 시각과 같습니다. 다음 두 경우는 예외입니다.
  - 사후 등록한 실험은 시작 시각과 시작 스냅샷이 비어 있거나, 사용자가 지정한 시점의 것이 됩니다.
  - 가져온 실험은 시작 시각과 시작 스냅샷이 비어 있고, 종료 시각은 가져온 시각이 됩니다.

본문은 다음 네 절로 고정되어 있습니다.

| 절 | 담는 내용 |
|---|---|
| 동기와 예상 | 무엇을 왜 해 보는지, 아이디어의 출처, 어떤 결과를 예상하는지 |
| 변경점 | 이 실험에서 무엇이 바뀌었는지. melog가 보여 주는 코드 비교를 참고해서 작성합니다. 기본 비교 대상은 시작 스냅샷이며, 수평 구조처럼 다른 파일을 복사해서 시작한 경우에는 사용자가 비교 대상을 고를 수 있습니다. |
| 결과 | 실험에서 관찰된 사실 |
| 메모 | 해석, 예상과 달랐던 점, 다음에 해 볼 것 |

## melog 프로젝트 설정

melog 프로젝트는 사용자가 명시적으로 만듭니다. 이름 외의 항목에는 모두 기본값이 있으므로, 이름만 정하면 바로 만들 수 있습니다.

| 항목 | 기본값 | 나중에 변경 | 설명 |
|---|---|---|---|
| 이름 | 없음 (필수) | 불가 | melog 프로젝트를 구분하는 이름입니다. 다른 프로젝트로 가져간 실험의 출처에 기록되므로 바꿀 수 없습니다. |
| 점수 구성 | CV, CV 표준편차, public LB | 가능 | melog가 기본으로 묻고 보여 줄 점수의 목록입니다. 실험 기록에 남길 수 있는 점수를 제한하지는 않습니다. |
| 수평 구조 여부 | 수평 구조가 아님 | 가능 | 수평 구조로 설정하면 하나의 작업 공간에서 여러 실험을 동시에 진행할 수 있습니다. 노트북은 수평으로 쌓더라도 공용 코드를 제자리에서 수정하는 혼합 구조에서는 스냅샷이 섞이므로, 순수한 수평 구조에서만 설정합니다. |
| 개요 | 비어 있음 | 가능 | 대회 정보, CV 전략, 데이터 스펙, 변경 이력 등을 자유롭게 적는 글입니다. 정해진 절은 없습니다. |

- 실험 기록은 점수의 이름과 값을 함께 저장합니다. 그래서 점수 구성을 바꿔도 이미 남긴 실험 기록은 영향을 받지 않고, 각 실험 기록은 프로젝트 설정 없이도 어떤 점수를 담고 있는지 알 수 있습니다.
- 수평 구조 여부는 실험을 시작할 때의 규칙에만 영향을 주므로, 바꿔도 이미 남긴 실험 기록에는 영향이 없습니다.

## 기록 절차

| 절차 | 사용자가 하는 일 | melog가 하는 일 |
|---|---|---|
| 시작 | 실험의 시작을 선언하고, 제목과 부모, 동기를 알려 줍니다 | id와 시작 시각을 발급하고, 시작 스냅샷을 남기고, 실험 기록을 만듭니다. 상태는 진행 중이 됩니다 |
| 완료 | 실험의 완료를 선언합니다. 점수와 판정, 본문은 이때 채워도 되고 나중에 채워도 됩니다 | 종료 시각과 종료 스냅샷을 남기고, 상태를 완료로 바꿉니다 |
| 중단 | 실험의 중단을 선언합니다 | 종료 시각과 종료 스냅샷을 남기고, 상태를 중단으로 바꿉니다 |
| 사후 등록 | 시작을 선언하지 않은 실험에 대해 시작과 완료를 한꺼번에 선언합니다. 시작 스냅샷으로 삼을 시점을 지정하거나 비워 둘 수 있습니다 | id와 시각을 발급하고, 종료 스냅샷을 남기고, 실험 기록을 만듭니다 |
| 가져오기 | 다른 melog 프로젝트에서 가져올 실험을 고릅니다 | 새 실험 기록을 만들고, 원래 실험의 종료 스냅샷을 이 실험의 종료 스냅샷으로 삼고, 출처를 기록합니다. 상태는 완료가 됩니다 |
| 보강 | 나중에 나온 점수(LB 등)나 고칠 내용을 알려 줍니다 | 실험 기록을 수정합니다 |

- **melog가 남긴 사실은 고칠 수 없고, 사용자가 채운 내용은 언제든 고칠 수 있습니다.** id, 시각, 코드 스냅샷, 출처, 상태는 고칠 수 없고, 제목, 부모, 진입점, 점수, 판정, 본문은 언제든 고칠 수 있습니다. 예외적으로, 아직 다른 사람과 공유하지 않은 실험의 id가 공유하는 과정에서 다른 실험의 id와 겹치면, melog가 그 id를 바꾸고 사용자에게 알립니다.
- **완료와 중단은 되돌릴 수 없는 최종 상태입니다.** 완료된 실험을 다시 진행하려면 새 실험을 시작합니다.
- **완료나 중단을 선언할 때 점수나 본문을 채우지 않아도 됩니다.** 본문은 나중에 채울 수 있지만 종료 스냅샷은 선언하는 시점에만 남길 수 있으므로, 선언하는 비용을 작게 유지합니다.
- **시작을 선언하지 않은 실험은 사후 등록으로 기록합니다.** 시작 스냅샷이 비어 있으면 변경점의 기본 비교 대상만 없을 뿐, 그 실험의 코드인 종료 스냅샷은 정상적으로 남습니다.
- **하나의 작업 공간에서는 진행 중인 실험을 하나만 둘 수 있습니다.** 코드 스냅샷은 코드 상태 전체를 남기므로, 같은 작업 공간에서 여러 실험을 동시에 진행하면 한 실험의 스냅샷에 다른 실험의 변경이 섞입니다. 여러 실험을 병렬로 진행하려면 작업 공간을 나눕니다. 다만 melog 프로젝트를 수평 구조로 설정하면 실험마다 파일이 분리되어 있다고 보고, 하나의 작업 공간에서 여러 실험을 동시에 진행할 수 있게 합니다.

## 추가 예정 항목

### 태그 (tags)

실험에 자유롭게 붙이는 분류 이름입니다(예: `feature`, `hyperparameter`). melog 프로젝트가 모델 단위처럼 큰 단위로 실험을 나눈다면, 태그는 하나의 melog 프로젝트 안에서 "피처 실험"이나 "하이퍼파라미터 조정"처럼 성격이 비슷한 실험을 묶는 데 씁니다. 보고서를 쓸 때 특정한 종류의 실험만 모아 보는 데 유용합니다.

## 개선할 점

### 명령줄에서 점수 구성 비우기

지금은 `melog init --scores ""`나 `melog project edit --scores ""`를 실행하면, 빈 점수 구성을 만드는 대신 "score names must not be empty" 오류가 납니다. 그래서 점수를 쓰지 않는 프로젝트라도 명령줄에서는 점수 구성을 빈 목록으로 만들 수 없습니다. 빈 문자열을 "점수 구성을 비운다"는 뜻으로 받아들이도록 바꾸는 것을 검토하고 있습니다.

### 이미 만든 스냅샷에서 비밀 정보 지우기

`.gitignore`에 넣지 않은 비밀 정보 파일(예: `.env`)은 코드 스냅샷에 들어갑니다. `.gitignore`에 나중에 추가하면 그 뒤의 스냅샷에서는 빠지지만, 이미 만든 스냅샷에는 그대로 남습니다. 그런데 지금은 이미 만든 스냅샷에서 특정 파일을 지우는 방법이 melog에 없습니다. 그래서 이런 스냅샷을 공유하지 않으려면 `melog sync`를 하지 않거나, 키를 새로 발급받아 남아 있는 키를 쓸모없게 만드는 수밖에 없습니다. git으로 melog의 참조를 직접 고치는 방법은 실험 기록과 스냅샷이 어긋날 수 있으므로 권하지 않습니다. 스냅샷에서 지정한 파일을 빼고 다시 만드는 명령을 검토하고 있습니다.

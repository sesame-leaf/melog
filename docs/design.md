# melog 구현 설계

[README.md](../README.md)가 melog의 목적과 개념을 다룬다면, 이 문서는 그 개념을 어떻게 구현할지 다룹니다. 이 문서에서 쓰는 용어는 README의 정의를 따릅니다.

## 인터페이스 원칙

1. **git의 내부 구조를 드러내지 않습니다.** 사용자는 전용 참조나 스냅샷 커밋 같은 개념을 몰라도 됩니다. 실험 기록을 보거나 고치거나 실험 코드를 재현할 때 git 명령을 직접 쓸 필요가 없어야 하며, 모든 작업은 melog 명령으로 할 수 있어야 합니다.
2. **명령어는 기록 절차와 대응합니다.** README의 기록 절차(시작, 완료, 중단, 사후 등록, 가져오기, 보강)에 조회와 편집, 코드 재현을 위한 명령 몇 가지만 더해서, 명령어의 수를 작게 유지합니다.
3. **사람과 에이전트가 같은 명령을 씁니다.** 에이전트 전용 명령을 따로 두지 않습니다. 사람이 쓸 때는 빠진 값을 대화형으로 묻고, 에이전트가 쓸 때는 같은 값을 옵션으로 받습니다. 에이전트가 결과를 읽기 쉽도록 기계가 읽을 수 있는 출력 형식도 제공합니다.
4. **본문은 익숙한 방식으로 편집합니다.** 실험 기록을 편집할 때는 사용자가 평소에 쓰는 에디터에서 일반 텍스트 문서로 열리게 합니다. 저장하면 melog가 그 내용을 전용 저장 공간에 반영합니다.
5. **사용자가 고칠 수 없는 항목은 편집 화면에서도 구분됩니다.** id, 시각, 스냅샷처럼 melog가 남긴 사실은 편집 대상에서 빠지거나 읽기 전용으로 표시됩니다.

## 코드 스냅샷

- 사용자가 실험의 시작이나 종료를 선언하면, 그 시점의 작업 트리 상태를 그대로 담은 **스냅샷 커밋**을 만듭니다.
- 스냅샷 커밋은 사용자의 브랜치, 스테이징 영역, 작업 트리를 건드리지 않고, **melog 전용 참조**(예: `refs/melog/...`)에만 저장합니다.
- 스냅샷에는 git이 추적하는 파일과, 아직 추적하지 않지만 `.gitignore`로 제외되지 않은 파일이 들어갑니다. 커밋하지 않은 변경도 스냅샷에 담깁니다.
- 스냅샷 커밋의 부모는 그 시점의 `HEAD`로 둡니다. 그래서 스냅샷이 사용자의 커밋 이력 중 어디에서 출발했는지도 함께 남습니다.
- 실험 기록은 스냅샷 커밋의 **해시를 직접 저장**합니다. 전용 참조는 스냅샷 커밋이 git의 정리 작업(gc)으로 지워지지 않도록 보존하는 역할만 맡습니다.

**이유**: 사용자의 브랜치에 커밋을 만들면, 사용자가 커밋하고 싶지 않은 시점에도 커밋이 생기므로 작업 방식에 개입하게 됩니다. 별도의 참조에 저장하면 사용자는 평소처럼 원하는 시점에 커밋하고, melog는 선언한 시점의 코드를 그대로 보존할 수 있습니다. 또한 실험 기록이 해시를 직접 담으면, 실험 기록만 보고도 어떤 코드를 가리키는지 알 수 있습니다. 가져온 실험이 원래 실험의 종료 스냅샷을 가리키는 것도 같은 해시를 적는 것으로 자연스럽게 표현됩니다.

## 실험 기록의 저장 위치

- 실험 기록과 melog 프로젝트 설정은 사용자의 브랜치와 독립된 **melog 전용 저장 공간**에 저장합니다. 어느 브랜치나 작업 공간에서 보아도 같은 실험 기록이 보입니다.
- 사용자는 저장 공간의 파일을 직접 열지 않고, melog가 실험 기록을 에디터로 열어 주는 기능으로 편집합니다.

**이유**: 실험 기록을 작업 트리 안의 파일로 두면 브랜치마다 실험 기록이 따로 존재합니다. 수직 구조에서 병렬로 실험하려면 작업 공간을 나눠야 하고, git worktree는 작업 공간마다 서로 다른 브랜치를 씁니다. 그런데 결과가 나빴거나 중단한 실험의 브랜치는 보통 병합하지 않고 버리므로, 그 실험의 기록이 메인 브랜치에 도달하지 못합니다. 이는 모든 실험을 빠짐없이 기록한다는 melog의 목적과 충돌합니다.

## 실험 기록의 파일 형식

- 실험 기록 하나를 Markdown 파일 하나로 저장합니다. 정형화된 항목은 파일 앞부분의 YAML frontmatter에 두고, 본문의 네 절은 Markdown 제목(`##`)으로 구분합니다.
- frontmatter는 melog가 YAML 라이브러리로 읽고 씁니다. 그래서 사용자가 따옴표 규칙 같은 형식의 세부 사항을 신경 쓸 필요가 없고, 점수처럼 중첩된 구조도 쓸 수 있습니다.
- 점수 값은 숫자만 받되, 사용자가 적은 표기를 그대로 보존합니다. 예를 들어 `0.80`은 `0.8`로 바뀌지 않습니다.
- 시각은 시간대를 포함한 ISO 8601 형식으로 저장하고, 화면에 보여 줄 때만 사용자의 시간대로 바꿉니다. 서로 다른 시간대에서 협업하더라도 실험의 순서를 정확히 판단하기 위해서입니다.

아래 예시에서 스냅샷 해시는 줄여서 표기했습니다.

```markdown
---
id: bjs-1
title: "LightGBM baseline"
status: done
started_at: 2026-11-09T14:30:00+09:00
ended_at: 2026-11-09T16:05:00+09:00
start_snapshot: 3f2a9c1e
end_snapshot: 8b7d4e02
parents: []
entry_points: [notebooks/baseline.ipynb]
scores:
  CV: 0.812
  CV std: 0.004
  public LB:
verdict: "baseline으로 충분히 쓸 만함"
---

## 동기와 예상

## 변경점

## 결과

## 메모
```

가져온 실험에는 출처가 함께 기록됩니다. 시작 시각과 시작 스냅샷은 비어 있고, 종료 스냅샷은 원래 실험의 종료 스냅샷과 같습니다.

```yaml
start_snapshot:
end_snapshot: 8b7d4e02
origin:
  project: lgbm
  id: bjs-3
  snapshot: 8b7d4e02
```

### 편집 화면

`melog edit`로 실험 기록을 열면, 에디터에는 저장된 파일과 조금 다른 편집용 문서가 열립니다.

- id, 상태, 시각, 스냅샷, 출처처럼 melog가 남긴 사실은 frontmatter 위에 **주석으로만** 보여 줍니다. 사용자가 주석을 고쳐도 melog는 무시합니다.
- frontmatter에는 사용자가 고칠 수 있는 항목(제목, 부모, 진입점, 점수, 판정)만 둡니다.
- 사용자가 저장하고 에디터를 닫으면, melog가 내용을 검증한 뒤 저장 공간에 반영합니다. 형식이 잘못되었거나, 존재하지 않는 실험을 부모로 적었거나, 부모 관계에 순환이 생기면 반영하지 않고 다시 편집할 기회를 줍니다.

### melog 프로젝트 설정과 개요

melog 프로젝트마다 저장하는 내용은 성격에 따라 두 파일로 나눕니다.

- **설정**(이름, 점수 구성, 수평 구조 여부)은 melog가 읽는 값이므로 YAML 파일 하나로 저장합니다.
- **개요**는 사용자가 자유롭게 쓰는 글이므로 Markdown 파일 하나로 저장하고, 실험 기록처럼 melog가 에디터로 열어 줍니다.
- melog 프로젝트의 이름에는 영문 소문자, 숫자, `-`, `_`만 쓸 수 있습니다. 이름이 전용 참조의 경로에 들어가기 때문입니다.

## id의 형식

id는 `{이니셜}-{순번}` 형식입니다(예: `bjs-1`, `bjs-12`).

- **이니셜**은 사람에 속한 값이므로 저장소가 아니라 사용자의 git 설정(`git config --global melog.initials`)에 저장합니다. 처음 실험을 시작할 때 이니셜이 설정되어 있지 않으면 melog가 묻고 저장합니다.
- 이니셜에는 영문 소문자와 숫자만 쓸 수 있습니다. id가 git 참조의 이름에도 들어가기 때문입니다.
- **순번**은 melog 프로젝트 안에서 같은 이니셜을 쓴 실험의 가장 큰 순번에 1을 더한 값입니다. 자릿수는 정하지 않으며, 앞에 0을 붙이지 않습니다.
- 순번의 자릿수가 일정하지 않으므로, 문자열 순서로 정렬하면 `bjs-10`이 `bjs-2`보다 앞에 옵니다. 그래서 melog가 실험을 정렬할 때는 순번을 숫자로 비교합니다.
- 같은 clone 안의 worktree끼리는 git 참조를 공유하므로 id가 겹치지 않습니다. 같은 사람이 서로 다른 clone에서 실험을 시작해서 id가 겹치는 경우는 "협업 방식" 절의 충돌 처리 규칙으로 해결합니다.

**이유**: 사람마다 번호 공간이 나뉘므로 여러 사람이 동시에 실험을 시작해도 충돌하지 않고, 짧아서 명령어에 직접 입력하기 쉽습니다.

## CLI 명령어 구성

| 분류 | 명령어 | 대응하는 절차 | 설명 |
|---|---|---|---|
| 프로젝트 | `melog init <이름>` | 프로젝트 생성 | melog 프로젝트를 만듭니다 |
| 프로젝트 | `melog project edit` | 설정 변경 | 옵션 없이 실행하면 개요를 에디터로 열고, 옵션을 주면 설정을 바꿉니다 |
| 기록 | `melog start <제목>` | 시작 | 부모와 동기, 진입점은 옵션으로 받습니다 |
| 기록 | `melog done [id]` | 완료, 사후 등록 | 점수와 판정은 옵션으로 받습니다. `--new <제목>`을 주면 시작을 선언하지 않은 실험을 사후 등록하며, 이때 시작 스냅샷으로 삼을 시점은 옵션으로 받습니다 |
| 기록 | `melog abandon [id]` | 중단 | |
| 기록 | `melog import <프로젝트>/<id>` | 가져오기 | |
| 기록 | `melog edit [id]` | 보강 | 옵션 없이 실행하면 에디터를 열고, 옵션을 주면 에디터 없이 해당 항목만 고칩니다 |
| 조회 | `melog show <id>` | | 실험 기록 하나를 보여 줍니다 |
| 조회 | `melog list` | | 실험 목록을 보여 줍니다 |
| 코드 | `melog diff <id>` | | 변경점을 쓸 때 참고할 코드 비교를 보여 줍니다. 기본 비교 대상은 시작 스냅샷이고, 옵션으로 다른 대상을 고를 수 있습니다 |
| 코드 | `melog checkout <id> [경로]` | | 실험의 종료 스냅샷을 별도의 디렉터리에 꺼내서 재현할 수 있게 합니다. 현재 작업 공간은 건드리지 않습니다 |
| 협업 | `melog sync` | | 실험 기록과 코드 스냅샷을 원격 저장소와 동기화합니다 |

- **`done`과 `abandon`의 id는 생략할 수 있습니다.** 수평 구조가 아닌 프로젝트에서는 한 작업 공간에 진행 중인 실험이 최대 하나이므로, id를 생략하면 이 작업 공간에서 진행 중인 실험을 가리킵니다. 수평 구조이면서 진행 중인 실험이 여럿이면 id를 지정해야 합니다.
- **수평 구조가 아닌 프로젝트에서는, 진행 중인 실험이 있는 작업 공간에서 사후 등록(`done --new`)을 거부합니다.** 사후 등록하는 실험의 종료 스냅샷에 진행 중인 실험의 변경이 섞이기 때문입니다. 이때 melog는 진행 중인 실험을 먼저 완료하거나 중단하라고 안내합니다. 중단한 실험은 나중에 부모로 삼아 다시 시작할 수 있다는 점도 함께 알려 줍니다.
- **`edit` 하나로 사람과 에이전트를 모두 지원합니다.** 사람은 옵션 없이 실행해서 에디터로 편집하고, 에이전트는 `melog edit bjs-3 --score "public LB=0.805"`처럼 옵션으로 고칩니다.
- **`show`와 `list`는 최소한의 조회 기능입니다.** id를 찾거나 방금 남긴 기록을 확인하는 데 필요한 정도만 제공합니다. 계보 보기와 실험 기록 모아 보기는 조회 기능을 설계할 때 따로 정합니다.
- **시작 스냅샷이 없는 실험의 `diff`는 비교 대상을 지정해야 합니다.** 사후 등록하거나 가져온 실험은 시작 스냅샷이 비어 있을 수 있으므로, 기본 비교 대상이 없으면 비교 대상을 지정하라고 안내합니다.
- **`checkout`은 git 용어를 그대로 쓴 이름입니다.** git의 내부 구조를 드러내지 않는다는 원칙의 예외이지만, "특정 시점의 코드를 꺼낸다"는 뜻이 개발자에게 바로 전달되므로 이 이름을 씁니다.
- **공통 옵션**: 모든 명령에 `--json`(기계가 읽을 수 있는 출력)과 `--project`(작업할 melog 프로젝트 지정)를 둡니다. `--project`를 생략하면 다음 순서로 프로젝트를 정합니다.
  1. 저장소에 melog 프로젝트가 하나뿐이면 그 프로젝트를 씁니다.
  2. 이 작업 공간에 진행 중인 실험이 있으면 그 실험의 프로젝트를 씁니다.
  3. 둘 다 해당하지 않으면 프로젝트 목록을 보여 주고, `--project`로 지정하라고 안내합니다.

## 협업 방식

### 공유

- 실험 기록과 코드 스냅샷은 `melog sync` 명령 하나로 공유합니다. 이 명령은 원격 저장소에서 가져오기, 병합, 올리기를 한꺼번에 수행합니다.
- git 설정을 바꿔서 평소의 `git fetch`나 `git push`에 전용 참조가 함께 포함되게 하는 방식은 쓰지 않습니다.

**이유**: git의 push 설정을 바꾸면 `git push`의 기본 동작 자체가 바뀌므로, 사용자가 예상하지 못한 동작이 생길 수 있습니다. 또한 git은 전용 참조를 병합해 주지 않으므로 충돌을 처리할 수 없습니다.

### 충돌 처리

| 대상 | 처리 |
|---|---|
| id | 같은 사람이 서로 다른 clone에서 sync 없이 실험을 시작하면 같은 id가 만들어질 수 있습니다. sync할 때 이를 감지하면, 아직 공유되지 않은 로컬 쪽 실험의 id를 다음 순번으로 바꿉니다. 로컬에서 그 실험을 부모로 선언한 실험도 함께 고치고, 바뀐 내용을 사용자에게 알립니다. 공유되기 전의 실험은 다른 사람이 부모로 참조했을 수 없으므로 id를 바꿔도 안전합니다 |
| 코드 스냅샷 | 한 번 남기면 고칠 수 없고 id가 겹치는 경우는 위 규칙으로 먼저 해결하므로, 충돌이 생기지 않습니다 |
| 서로 다른 실험 기록 | id가 사람마다 나뉘어 있으므로 대부분 서로 다른 파일을 고칩니다. 이 경우 자동으로 병합합니다 |
| 같은 실험 기록 | 고친 항목이 서로 다르면 자동으로 병합합니다. 같은 항목을 서로 다르게 고쳤을 때만 사용자에게 어느 쪽을 남길지 묻습니다 |

## 작업 공간과 진행 중인 실험의 연결

- "이 작업 공간에서 진행 중인 실험"이라는 정보는 공유하지 않고, 작업 공간마다 로컬에 따로 저장합니다.
- 저장 위치는 git이 worktree마다 따로 두는 내부 디렉터리입니다. 그래서 작업 공간끼리 섞이지 않고, `melog sync`로 다른 사람에게 공유되지도 않습니다.

**이유**: 실험 기록은 모든 작업 공간과 모든 사람이 공유하므로, 실험 기록만 보고는 어느 실험이 이 작업 공간에서 진행 중인지 알 수 없습니다. 그런데 melog는 `done`이나 `abandon`의 id를 생략했을 때 이 작업 공간의 실험을 찾아야 하고, 작업 공간 규칙도 검사해야 합니다.

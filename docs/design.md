# melog 구현 설계

[README.md](../README.md)가 melog의 목적과 개념을 다룬다면, 이 문서는 그 개념을 어떻게 구현할지 다룹니다. 이 문서에서 쓰는 용어는 README의 정의를 따릅니다. 구현 순서와 진행 상황은 [plan.md](plan.md)에서 다룹니다.

## 인터페이스 원칙

1. **git의 내부 구조를 드러내지 않습니다.** 사용자는 전용 참조나 스냅샷 커밋 같은 개념을 몰라도 됩니다. 실험 기록을 보거나 고치거나 실험 코드를 재현할 때 git 명령을 직접 쓸 필요가 없어야 하며, 모든 작업은 melog 명령으로 할 수 있어야 합니다.
2. **명령어는 기록 절차와 대응합니다.** README의 기록 절차(시작, 완료, 중단, 사후 등록, 가져오기, 보강)에 조회와 편집, 코드 재현을 위한 명령 몇 가지만 더해서, 명령어의 수를 작게 유지합니다.
3. **사람과 에이전트가 같은 명령을 씁니다.** 에이전트 전용 명령을 따로 두지 않습니다. 사람이 쓸 때는 빠진 값을 대화형으로 묻고, 에이전트가 쓸 때는 같은 값을 옵션으로 받습니다. 에이전트가 결과를 읽기 쉽도록 기계가 읽을 수 있는 출력 형식도 제공합니다.
4. **본문은 익숙한 방식으로 편집합니다.** 실험 기록을 편집할 때는 사용자가 평소에 쓰는 에디터에서 일반 텍스트 문서로 열리게 합니다. 저장하면 melog가 그 내용을 전용 저장 공간에 반영합니다.
5. **사용자가 고칠 수 없는 항목은 편집 화면에서도 구분됩니다.** id, 시각, 스냅샷처럼 melog가 남긴 사실은 편집 대상에서 빠지거나 읽기 전용으로 표시됩니다.

### 언어

- CLI가 출력하는 메시지(안내, 오류, 확인 문구)와 `--json` 출력의 키는 영어로 씁니다.
- 실험 기록 본문의 절 제목(동기와 예상, 변경점, 결과, 메모)은 한국어로 씁니다.

## 코드 스냅샷

- 사용자가 실험의 시작이나 종료를 선언하면, 그 시점의 작업 트리 상태를 그대로 담은 **스냅샷 커밋**을 만듭니다.
- 스냅샷 커밋은 사용자의 브랜치, 스테이징 영역, 작업 트리를 건드리지 않고, **melog 전용 참조**(예: `refs/melog/...`)에만 저장합니다.
- 스냅샷에는 git이 추적하는 파일과, 아직 추적하지 않지만 `.gitignore`로 제외되지 않은 파일이 들어갑니다. 커밋하지 않은 변경도 스냅샷에 담깁니다.
- 스냅샷 커밋의 부모는 그 시점의 `HEAD`로 둡니다. 그래서 스냅샷이 사용자의 커밋 이력 중 어디에서 출발했는지도 함께 남습니다.
- 실험 기록은 스냅샷 커밋의 **해시를 직접 저장**합니다. 전용 참조는 스냅샷 커밋이 git의 정리 작업(gc)으로 지워지지 않도록 보존하는 역할만 맡습니다. 보존용 참조의 이름은 `refs/melog/snapshots/<프로젝트>/<id>/start`와 `.../end`입니다.
- git이 추적하지 않는 파일 중 10MB를 넘는 파일이 스냅샷에 들어가면, 파일 목록과 함께 경고를 보여 줍니다. 경고만 하고 스냅샷을 막지는 않습니다. `.gitignore`에 넣지 않은 데이터 파일이 스냅샷에 들어가면 저장소의 크기가 빠르게 커지기 때문입니다.

**이유**: 사용자의 브랜치에 커밋을 만들면, 사용자가 커밋하고 싶지 않은 시점에도 커밋이 생기므로 작업 방식에 개입하게 됩니다. 별도의 참조에 저장하면 사용자는 평소처럼 원하는 시점에 커밋하고, melog는 선언한 시점의 코드를 그대로 보존할 수 있습니다. 또한 실험 기록이 해시를 직접 담으면, 실험 기록만 보고도 어떤 코드를 가리키는지 알 수 있습니다. 가져온 실험이 원래 실험의 종료 스냅샷을 가리키는 것도 같은 해시를 적는 것으로 자연스럽게 표현됩니다.

## 실험 기록의 저장 위치

- 실험 기록과 melog 프로젝트 설정은 사용자의 브랜치와 독립된 **melog 전용 저장 공간**에 저장합니다. 어느 브랜치나 작업 공간에서 보아도 같은 실험 기록이 보입니다.
- 사용자는 저장 공간의 파일을 직접 열지 않고, melog가 실험 기록을 에디터로 열어 주는 기능으로 편집합니다.
- 저장 공간은 `refs/melog/store` 참조가 가리키는 커밋입니다. 그 안에서 melog 프로젝트마다 설정은 `<프로젝트>/project.yaml`, 개요는 `<프로젝트>/overview.md`, 실험 기록은 `<프로젝트>/records/<id>.md`에 둡니다.

**이유**: 실험 기록을 작업 트리 안의 파일로 두면 브랜치마다 실험 기록이 따로 존재합니다. 수직 구조에서 병렬로 실험하려면 작업 공간을 나눠야 하고, git worktree는 작업 공간마다 서로 다른 브랜치를 씁니다. 그런데 결과가 나빴거나 중단한 실험의 브랜치는 보통 병합하지 않고 버리므로, 그 실험의 기록이 메인 브랜치에 도달하지 못합니다. 이는 모든 실험을 빠짐없이 기록한다는 melog의 목적과 충돌합니다.

## 실험 기록의 파일 형식

- 실험 기록 하나를 Markdown 파일 하나로 저장합니다. 정형화된 항목은 파일 앞부분의 YAML frontmatter에 두고, 본문의 네 절은 Markdown 제목(`##`)으로 구분합니다.
- frontmatter는 melog가 YAML 라이브러리로 읽고 씁니다. 그래서 사용자가 따옴표 규칙 같은 형식의 세부 사항을 신경 쓸 필요가 없고, 점수처럼 중첩된 구조도 쓸 수 있습니다.
- 점수 값은 숫자만 받되, 사용자가 적은 표기를 그대로 보존합니다. 예를 들어 `0.80`은 `0.8`로 바뀌지 않습니다.
- 시각은 시간대를 포함한 ISO 8601 형식으로 저장하고, 화면에 보여 줄 때만 사용자의 시간대로 바꿉니다. 서로 다른 시간대에서 협업하더라도 실험의 순서를 정확히 판단하기 위해서입니다.

아래 예시에서 스냅샷 해시는 줄여서 표기했습니다.

```markdown
---
id: bjs-1
title: "LightGBM baseline"
status: done
started_at: 2026-11-09T14:30:00+09:00
ended_at: 2026-11-09T16:05:00+09:00
start_snapshot: 3f2a9c1e
end_snapshot: 8b7d4e02
parents: []
entry_points: [notebooks/baseline.ipynb]
scores:
  CV: 0.812
  CV std: 0.004
  public LB:
verdict: "baseline으로 충분히 쓸 만함"
---

## 동기와 예상

## 변경점

## 결과

## 메모
```

가져온 실험에는 출처가 함께 기록됩니다. 시작 시각과 시작 스냅샷은 비어 있고, 종료 스냅샷은 원래 실험의 종료 스냅샷과 같습니다.

```yaml
start_snapshot:
end_snapshot: 8b7d4e02
origin:
  project: lgbm
  id: bjs-3
  snapshot: 8b7d4e02
```

### 편집 화면

`melog edit`로 실험 기록을 열면, 에디터에는 저장된 파일과 조금 다른 편집용 문서가 열립니다. 에디터는 git이 쓰는 에디터 설정(`GIT_EDITOR`, `core.editor`, `VISUAL`, `EDITOR`의 순서)을 그대로 따릅니다.

- id, 상태, 시각, 스냅샷, 출처처럼 melog가 남긴 사실은 frontmatter 안의 맨 위에 **YAML 주석으로만** 보여 줍니다. 사용자가 주석을 고쳐도 melog는 무시합니다. 주석을 frontmatter 밖이 아닌 안에 두는 이유는, 편집용 문서 전체가 올바른 Markdown + frontmatter 형식으로 남아서 에디터의 문법 강조가 제대로 동작하기 때문입니다.
- frontmatter에는 사용자가 고칠 수 있는 항목(제목, 부모, 진입점, 점수, 판정)만 둡니다.

```markdown
---
# melog: editing bjs-3 in project lgbm
# Recorded by melog, cannot be changed here:
#   status:  done
#   started: 2026-11-09 14:30
#   ended:   2026-11-09 16:05
# Save and close the editor to apply. Delete everything to cancel.
title: LightGBM baseline
parents: [bjs-1]
entry_points: [train.py]
scores:
  CV: 0.812
  CV std: 0.004
  public LB:
verdict: 베이스라인으로 쓸 만함
---

## 동기와 예상

## 변경점

## 결과

## 메모
```

사용자가 저장하고 에디터를 닫으면 다음과 같이 처리합니다.

| 상황 | 동작 |
|---|---|
| 아무것도 바꾸지 않고 닫음 | 아무것도 반영하지 않습니다 |
| 내용을 전부 지우고 저장함 | 편집을 취소합니다 |
| 검증을 통과함 | 저장 공간에 반영하고, 바뀐 항목을 알려 줍니다 |
| 검증에 실패함 | 오류를 보여 주고 다시 편집할지 묻습니다. 다시 편집하면 사용자가 고친 내용을 그대로 다시 엽니다. 다시 편집하지 않으면 고친 내용을 임시 파일로 남기고 그 경로를 알려 줍니다 |

검증 항목은 다음과 같습니다.

- 제목이 비어 있지 않아야 합니다.
- 부모는 같은 프로젝트에 있는 실험이어야 하고, 자기 자신이 아니어야 하며, 부모 관계에 순환이 없어야 합니다.
- 점수 값은 숫자이거나 비어 있어야 합니다.
- frontmatter에 모르는 항목이나 고칠 수 없는 항목이 있으면 오류로 처리합니다. 항목 이름을 잘못 적었을 때 그 내용이 조용히 사라지는 일을 막기 위해서입니다.
- 본문의 네 절 제목은 각각 정확히 한 번씩 있어야 합니다. 절 제목 하나를 실수로 지우면 그 절의 내용이 앞 절에 섞여 들어가기 때문입니다.

### 편집하는 동안 다른 곳에서 같은 기록을 고친 경우

에디터를 열어 둔 동안 다른 작업 공간에서 같은 실험 기록을 고칠 수 있습니다. 이때는 협업 방식의 충돌 처리와 같은 규칙을 따릅니다. 사용자가 고친 항목만 반영하고, 같은 항목을 양쪽에서 서로 다르게 고친 경우에만 오류를 냅니다. 점수는 점수 이름마다, 본문은 절마다 따로 비교합니다. 오류가 나면 고친 내용을 임시 파일로 남기고 그 경로를 알려 줍니다.

### melog 프로젝트 설정과 개요

melog 프로젝트마다 저장하는 내용은 성격에 따라 두 파일로 나눕니다.

- **설정**(이름, 점수 구성, 수평 구조 여부)은 melog가 읽는 값이므로 YAML 파일 하나로 저장합니다.
- **개요**는 사용자가 자유롭게 쓰는 글이므로 Markdown 파일 하나로 저장하고, 실험 기록처럼 melog가 에디터로 열어 줍니다.
- melog 프로젝트의 이름에는 영문 소문자, 숫자, `-`, `_`만 쓸 수 있습니다. 이름이 전용 참조의 경로에 들어가기 때문입니다. 또한 이름은 영문 소문자나 숫자로 시작해야 하며, `-`나 `_`로 시작할 수 없습니다. `melog init -lgbm`처럼 `-`로 시작하는 이름은 명령어에서 옵션으로 해석되기 때문입니다.

## id의 형식

id는 `{이니셜}-{순번}` 형식입니다(예: `bjs-1`, `bjs-12`).

- **이니셜**은 사람에 속한 값이므로 저장소가 아니라 사용자의 git 설정(`git config --global melog.initials`)에 저장합니다. 처음 실험을 시작할 때 이니셜이 설정되어 있지 않으면 melog가 묻고 저장합니다. 터미널에서 실행하지 않았거나 `--json`을 준 경우에는 묻지 않고, 설정하는 방법을 안내한 뒤 종료합니다.
- 이니셜에는 영문 소문자와 숫자만 쓸 수 있습니다. id가 git 참조의 이름에도 들어가기 때문입니다.
- **순번**은 melog 프로젝트 안에서 같은 이니셜을 쓴 실험의 가장 큰 순번에 1을 더한 값입니다. 자릿수는 정하지 않으며, 앞에 0을 붙이지 않습니다.
- 순번의 자릿수가 일정하지 않으므로, 문자열 순서로 정렬하면 `bjs-10`이 `bjs-2`보다 앞에 옵니다. 그래서 melog가 실험을 정렬할 때는 순번을 숫자로 비교합니다.
- 같은 clone 안의 worktree끼리는 git 참조를 공유하므로 id가 겹치지 않습니다. 같은 사람이 서로 다른 clone에서 실험을 시작해서 id가 겹치는 경우는 "협업 방식" 절의 충돌 처리 규칙으로 해결합니다.

**이유**: 사람마다 번호 공간이 나뉘므로 여러 사람이 동시에 실험을 시작해도 충돌하지 않고, 짧아서 명령어에 직접 입력하기 쉽습니다.

## CLI 명령어 구성

| 분류 | 명령어 | 대응하는 절차 | 설명 |
|---|---|---|---|
| 프로젝트 | `melog init <이름>` | 프로젝트 생성 | melog 프로젝트를 만듭니다 |
| 프로젝트 | `melog project edit` | 설정 변경 | 옵션 없이 실행하면 개요를 에디터로 열고, 옵션을 주면 설정을 바꿉니다 |
| 기록 | `melog start <제목>` | 시작 | 부모와 동기, 진입점은 옵션으로 받습니다 |
| 기록 | `melog done [id]` | 완료, 사후 등록 | 점수와 판정은 옵션으로 받습니다. `--new <제목>`을 주면 시작을 선언하지 않은 실험을 사후 등록하며, 이때 시작 스냅샷으로 삼을 시점은 옵션으로 받습니다 |
| 기록 | `melog abandon [id]` | 중단 | |
| 기록 | `melog import <프로젝트>/<id>` | 가져오기 | |
| 기록 | `melog edit [id]` | 보강 | 옵션 없이 실행하면 에디터를 열고, 옵션을 주면 에디터 없이 해당 항목만 고칩니다 |
| 조회 | `melog show <id>` | | 실험 기록 하나를 보여 줍니다 |
| 조회 | `melog list` | | 실험 목록을 보여 줍니다 |
| 코드 | `melog diff <id>` | | 변경점을 쓸 때 참고할 코드 비교를 보여 줍니다. 기본 비교 대상은 시작 스냅샷이고, 옵션으로 다른 대상을 고를 수 있습니다 |
| 코드 | `melog checkout <id> [경로]` | | 실험의 종료 스냅샷을 별도의 디렉터리에 꺼내서 재현할 수 있게 합니다. 현재 작업 공간은 건드리지 않습니다 |
| 협업 | `melog sync` | | 실험 기록과 코드 스냅샷을 원격 저장소와 동기화합니다. 세부 동작은 "협업 방식" 절에서 다룹니다 |

- **`done`과 `abandon`의 id는 생략할 수 있습니다.** 수평 구조가 아닌 프로젝트에서는 한 작업 공간에 진행 중인 실험이 최대 하나이므로, id를 생략하면 이 작업 공간에서 진행 중인 실험을 가리킵니다. 수평 구조이면서 진행 중인 실험이 여럿이면 id를 지정해야 합니다.
- **수평 구조가 아닌 프로젝트에서는, 진행 중인 실험이 있는 작업 공간에서 사후 등록(`done --new`)을 거부합니다.** 사후 등록하는 실험의 종료 스냅샷에 진행 중인 실험의 변경이 섞이기 때문입니다. 이때 melog는 진행 중인 실험을 먼저 완료하거나 중단하라고 안내합니다. 중단한 실험은 나중에 부모로 삼아 다시 시작할 수 있다는 점도 함께 알려 줍니다.
- **`edit` 하나로 사람과 에이전트를 모두 지원합니다.** 사람은 옵션 없이 실행해서 에디터로 편집하고, 에이전트는 `melog edit bjs-3 --score "public LB=0.805"`처럼 옵션으로 고칩니다. 옵션 방식의 세부 동작은 아래 "편집 명령의 세부 동작"에서 다룹니다.
- **`show`와 `list`는 최소한의 조회 기능입니다.** id를 찾거나 방금 남긴 기록을 확인하는 데 필요한 정도만 제공합니다. 계보 보기와 실험 기록 모아 보기는 조회 기능을 설계할 때 따로 정합니다.
- **시작 스냅샷이 없는 실험의 `diff`는 비교 대상을 지정해야 합니다.** 사후 등록하거나 가져온 실험은 시작 스냅샷이 비어 있을 수 있으므로, 기본 비교 대상이 없으면 비교 대상을 지정하라고 안내합니다.
- **`checkout`은 git 용어를 그대로 쓴 이름입니다.** git의 내부 구조를 드러내지 않는다는 원칙의 예외이지만, "특정 시점의 코드를 꺼낸다"는 뜻이 개발자에게 바로 전달되므로 이 이름을 씁니다.
- **공통 옵션**: 모든 명령에 `--json`(기계가 읽을 수 있는 출력)과 `--project`(작업할 melog 프로젝트 지정)를 둡니다. `--project`를 생략하면 다음 순서로 프로젝트를 정합니다.
  1. 저장소에 melog 프로젝트가 하나뿐이면 그 프로젝트를 씁니다.
  2. 이 작업 공간에 진행 중인 실험이 있으면 그 실험의 프로젝트를 씁니다.
  3. 둘 다 해당하지 않으면 프로젝트 목록을 보여 주고, `--project`로 지정하라고 안내합니다.

### 기록 명령의 세부 동작

| 명령어 | 옵션 | 동작 |
|---|---|---|
| `start [제목]` | `--parent ID`(여러 번), `--motivation TEXT`, `--entry PATH`(여러 번) | 부모가 같은 프로젝트에 있는지와 작업 공간 규칙을 검사한 뒤, id를 발급하고 시작 스냅샷을 남깁니다. 점수 구성에 있는 점수는 빈 값으로 미리 채워 둡니다 |
| `done [ID]` | `--score NAME=VALUE`(여러 번), `--verdict TEXT`, `--force` | 종료 스냅샷과 종료 시각을 남기고 상태를 완료로 바꿉니다. 점수 값은 숫자여야 하고, 점수 구성에 없는 이름도 쓸 수 있습니다 |
| `done --new 제목` | `--since REV`와 `start`의 옵션 | 사후 등록입니다. ID와 함께 쓸 수 없습니다. `--since`에는 커밋 해시나 `HEAD~2` 같은 git 리비전을 주며, 시작 스냅샷은 그 커밋이 되고 시작 시각은 그 커밋의 시각이 됩니다 |
| `abandon [ID]` | `--verdict TEXT`, `--force` | 종료 스냅샷과 종료 시각을 남기고 상태를 중단으로 바꿉니다 |
| `show ID` | | 정형화된 항목과 본문 네 절을 보여 줍니다. 시각은 사용자의 시간대로 바꿔서 보여 줍니다 |
| `list` | `--status STATUS` | 한 줄에 실험 하나씩 id, 상태, 제목, 점수 구성에 있는 점수를 보여 줍니다. 이 작업 공간에서 진행 중인 실험에는 `*`를 붙입니다 |

- `done`과 `abandon`의 ID를 생략했는데 이 작업 공간에서 진행 중인 실험이 여러 개면, 목록을 보여 주면서 ID를 지정하라고 안내합니다.
- `list`는 시작 시각 순서로 정렬하고, 시작 시각이 없으면 종료 시각을 씁니다. 시각이 같으면 id 순서로 정렬합니다. 여러 사람의 실험이 섞여 있을 때는 시간 순서가 가장 읽기 쉽기 때문입니다.

### 대화형 입력

터미널에서 실행했고 `--json`을 주지 않았을 때만, 빠진 값을 묻습니다. 모든 질문은 Enter로 건너뛸 수 있습니다.

- `start`: 제목이 없으면 제목을 묻고, `--motivation`이 없으면 동기를 묻습니다. 부모는 묻지 않고 옵션으로만 받습니다.
- `done`: 점수 구성에 있는 점수 중 옵션으로 주지 않은 것과 판정을 차례로 묻습니다. 점수 구성은 melog가 기본으로 묻는 점수의 목록이기 때문입니다.

### 편집 명령의 세부 동작

`melog edit [ID]`는 옵션을 하나라도 주면 에디터를 열지 않고 지정한 항목만 고칩니다. 옵션이 없으면 에디터를 엽니다. ID를 생략하면 이 작업 공간에서 진행 중인 실험을 대상으로 삼고, 진행 중인 실험이 없으면 ID를 지정하라고 안내합니다. 터미널에서 실행하지 않았거나 `--json`을 준 상태에서 옵션 없이 실행하면, 에디터를 열 수 없으므로 옵션을 지정하라고 안내합니다.

| 옵션 | 동작 |
|---|---|
| `--title TEXT` | 제목을 바꿉니다 |
| `--parent ID`(여러 번) | 부모 목록 전체를 주어진 목록으로 바꿉니다 |
| `--clear-parents` | 부모를 모두 지웁니다 |
| `--entry PATH`(여러 번) | 진입점 목록 전체를 주어진 목록으로 바꿉니다 |
| `--clear-entries` | 진입점을 모두 지웁니다 |
| `--score NAME=VALUE`(여러 번) | 점수를 정합니다. `NAME=`처럼 값을 비우면 그 점수를 빈 값으로 만듭니다 |
| `--verdict TEXT` | 판정을 바꿉니다. 빈 문자열을 주면 지웁니다 |
| `--motivation`, `--changes`, `--result`, `--memo` | 본문의 각 절(동기와 예상, 변경점, 결과, 메모)을 주어진 내용으로 바꿉니다. 값으로 `-`를 주면 표준 입력에서 내용을 읽습니다. 표준 입력은 하나뿐이므로 `-`는 한 번에 한 옵션에만 쓸 수 있습니다 |

`melog project edit`을 옵션 없이 실행하면 개요를 에디터로 엽니다. 개요는 자유 서술이므로 검증하지 않고, 비운 채 저장하면 개요가 비워집니다. 에디터를 열어 둔 동안 다른 곳에서 개요를 고쳤다면, 덮어쓰지 않고 고친 내용을 임시 파일로 남깁니다.

### 코드 명령의 세부 동작

`melog diff ID [PATH...]`는 변경점 절을 쓸 때 참고할 코드 비교를 보여 줍니다. 경로를 주면 그 경로만 비교합니다.

| 상황 | 비교 기준 → 비교 대상 |
|---|---|
| 기본 (완료되거나 중단된 실험) | 시작 스냅샷 → 종료 스냅샷 |
| 진행 중인 실험 | 시작 스냅샷 → 현재 작업 트리. 실험을 끝내기 전에 변경점을 미리 정리할 때 씁니다 |
| `--against OTHER` | OTHER → 이 실험의 코드. OTHER가 실험 id이면 그 실험의 종료 스냅샷을 쓰고, 그렇지 않으면 git 리비전으로 해석합니다 |
| 시작 스냅샷이 없음 (사후 등록, 가져오기) | `--against`를 지정하라고 안내합니다 |

| 옵션 | 동작 |
|---|---|
| `--entry-points` | 파일 경로가 아니라 진입점끼리 비교합니다. 수평 구조에서 부모의 노트북과 이 실험의 노트북을 비교할 때 씁니다. 두 실험의 진입점 개수가 같아야 하며, 기록된 순서대로 짝을 짓습니다 |
| `--stat` | 바뀐 파일의 목록과 바뀐 줄 수만 보여 줍니다 |
| `--raw` | 노트북도 원래의 JSON 그대로 비교합니다 |

- 노트북(`.ipynb`)은 기본적으로 **코드 셀의 코드만** 비교합니다. 실행 결과, 실행 번호, 메타데이터의 변경이 섞이면 무엇이 바뀌었는지 읽기 어렵기 때문입니다.
- 터미널에서 실행하면 git처럼 색을 입히고, git의 페이저 설정(`GIT_PAGER`, `core.pager`)을 따라 페이저로 보여 줍니다.

`melog checkout ID [경로]`는 실험의 코드를 별도의 디렉터리에 꺼냅니다. 현재 작업 공간은 건드리지 않습니다.

- 기본적으로 종료 스냅샷을 꺼내고, `--start`를 주면 시작 스냅샷을 꺼냅니다. 진행 중인 실험은 종료 스냅샷이 없으므로 `--start`가 필요합니다.
- 꺼낸 디렉터리는 **git worktree**입니다. 그래서 꺼낸 디렉터리가 하나의 작업 공간이 되고, 그 안에서 `melog start --parent bjs-3`처럼 예전 실험의 코드에서 바로 새 실험을 시작할 수 있습니다.
- 경로를 생략하면 저장소 옆에 `<저장소 이름>-<id>` 디렉터리(예: `../titanic-bjs-3`)를 만듭니다. 저장소 안에 만들면 `git status`에 추적하지 않는 디렉터리로 나타나기 때문입니다. 이미 있는 경로라면 오류를 냅니다.
- 꺼낸 뒤에는 git이 무시하는 파일(데이터, 모델 가중치 등)은 포함되지 않는다는 점과, 다 쓴 디렉터리를 지우는 방법(`git worktree remove`)을 안내합니다. 지우는 명령은 필요해지면 추가합니다.

### 가져오기의 세부 동작

`melog import <프로젝트>/<id>`는 다른 melog 프로젝트의 실험을, `--project`로 정한 프로젝트의 새 실험으로 만듭니다.

| 항목 | 가져온 실험의 값 |
|---|---|
| 제목 | 원래 실험의 제목. `--title`로 바꿀 수 있습니다 |
| 진입점 | 원래 실험의 진입점. 종료 스냅샷이 같으므로 경로도 그대로 유효합니다 |
| 동기와 예상 | `--motivation`으로 받고, 터미널에서는 `start`처럼 묻습니다. "왜 가져왔는가"는 이 프로젝트에서 새로 생긴 맥락이기 때문입니다 |
| 점수 | 이 프로젝트의 점수 구성을 빈 값으로 채워 둡니다 |
| 판정, 변경점, 결과, 메모 | 비워 둡니다. 원래 실험에 대한 판단은 이 프로젝트에서의 판단과 다를 수 있기 때문입니다 |

| 경우 | 동작 |
|---|---|
| 원래 실험이 진행 중임 | 종료 스냅샷이 없으므로 거부합니다 |
| 원래 실험이 중단됨 | 허용합니다. 그 코드를 쓸지는 사용자가 판단합니다 |
| 같은 프로젝트의 실험 | 거부하고, `--parent`로 부모를 선언하라고 안내합니다 |
| 이미 가져온 실험 | 거부하고, 이미 가져온 실험의 id를 알려 주면서 그 실험을 부모로 쓰라고 안내합니다. 같은 코드를 두 번 가져오는 것은 대부분 실수이기 때문입니다 |

가져오기는 현재 작업 트리의 스냅샷을 남기지 않으므로, 작업 공간 규칙을 검사하지 않습니다. 진행 중인 실험이 있는 작업 공간에서도 가져올 수 있습니다.

## 협업 방식

### 공유

- 실험 기록과 코드 스냅샷은 `melog sync` 명령 하나로 공유합니다. 이 명령은 원격 저장소에서 가져오기, 병합, 올리기를 한꺼번에 수행합니다.
- git 설정을 바꿔서 평소의 `git fetch`나 `git push`에 전용 참조가 함께 포함되게 하는 방식은 쓰지 않습니다.

**이유**: git의 push 설정을 바꾸면 `git push`의 기본 동작 자체가 바뀌므로, 사용자가 예상하지 못한 동작이 생길 수 있습니다. 또한 git은 전용 참조를 병합해 주지 않으므로 충돌을 처리할 수 없습니다.

### 충돌 처리

| 대상 | 처리 |
|---|---|
| id | 같은 사람이 서로 다른 clone에서 sync 없이 실험을 시작하면 같은 id가 만들어질 수 있습니다. sync할 때 이를 감지하면, 아직 공유되지 않은 로컬 쪽 실험의 id를 다음 순번으로 바꿉니다. 로컬에서 그 실험을 부모로 선언한 실험도 함께 고치고, 바뀐 내용을 사용자에게 알립니다. 공유되기 전의 실험은 다른 사람이 부모로 참조했을 수 없으므로 id를 바꿔도 안전합니다 |
| 코드 스냅샷 | 한 번 남기면 고칠 수 없고 id가 겹치는 경우는 위 규칙으로 먼저 해결하므로, 충돌이 생기지 않습니다 |
| 서로 다른 실험 기록 | id가 사람마다 나뉘어 있으므로 대부분 서로 다른 파일을 고칩니다. 이 경우 자동으로 병합합니다 |
| 같은 실험 기록 | 고친 항목이 서로 다르면 자동으로 병합합니다. 같은 항목을 서로 다르게 고쳤을 때만 사용자에게 어느 쪽을 남길지 묻습니다 |

### `melog sync`의 세부 동작

```
melog sync [--remote NAME] [--prefer local|remote] [--yes] [--json]
```

1. **가져오기**: 원격 저장소의 실험 기록과 코드 스냅샷을 가져옵니다. 가져온 내용은 원격 저장소의 상태를 보관하는 별도의 참조(`refs/melog/remotes/<원격 저장소>/...`)에 두므로, 이 단계에서는 로컬의 실험 기록이 바뀌지 않습니다.
2. **id 충돌 해결**: 같은 id의 실험 기록이 양쪽에 따로 만들어졌다면, 아직 공유되지 않은 로컬 쪽 실험의 id를 다음 순번으로 바꿉니다. 이때 다음을 함께 고칩니다.
   - 실험 기록 자체의 id와 파일 이름
   - 그 실험의 코드 스냅샷 보존용 참조
   - 로컬에서 그 실험을 부모로 선언한 다른 실험의 부모 목록
   - 이 clone에 있는 모든 작업 공간(worktree)의 "진행 중인 실험" 정보
3. **병합**: 실험 기록, 프로젝트 설정, 개요를 병합해서 하나의 병합 커밋으로 남깁니다. 2번의 id 변경도 이 커밋에 함께 들어가므로, 병합이 실패하면 id도 바뀌지 않습니다.
4. **올리기**: 병합한 결과와 로컬의 코드 스냅샷을 원격 저장소에 한 번에(atomic) 올립니다. 그 사이에 다른 사람이 먼저 올렸다면, 1번부터 다시 시도합니다.

동작 규칙은 다음과 같습니다.

| 주제 | 규칙 |
|---|---|
| 원격 저장소 | 기본값은 `origin`이고 `--remote`로 바꿀 수 있습니다. 해당 원격 저장소가 없으면 원격 저장소 목록을 보여 주면서 `--remote`로 지정하라고 안내합니다 |
| 병합 단위 | 본문의 각 절과 개요는 git처럼 **줄 단위**로 병합해서, 같은 줄 근처를 양쪽에서 고친 경우만 충돌로 처리합니다. 제목, 판정, 점수(이름마다), 부모, 진입점, 설정, 그리고 상태나 종료 스냅샷처럼 melog가 남긴 사실은 항목 전체를 하나의 단위로 비교합니다 |
| 충돌 해결 | 터미널에서는 충돌한 항목마다 로컬 값과 원격 값을 보여 주고 어느 쪽을 남길지 묻습니다. 터미널이 아니면 충돌 목록을 보여 주고 아무것도 바꾸지 않은 채 종료합니다. `--prefer local` 또는 `--prefer remote`를 주면 그쪽 값으로 충돌을 모두 해결합니다 |
| 동기화 시점 | `melog sync`를 실행했을 때만 동기화합니다. 다른 명령은 자동으로 동기화하지 않습니다. 네트워크가 없는 환경에서도 기록이 끊기지 않아야 하기 때문입니다 |
| 처음 올릴 때의 확인 | 코드 스냅샷에는 커밋하지 않은 파일도 들어가므로, `.gitignore`에 넣지 않은 파일(예: `.env`)도 함께 공유됩니다. 그래서 원격 저장소마다 처음 올릴 때 한 번, 올라갈 스냅샷에 새로 들어간 파일 목록을 보여 주고 확인을 받습니다. 터미널이 아니면 `--yes`를 주어야 진행합니다 |


- "이 작업 공간에서 진행 중인 실험"이라는 정보는 공유하지 않고, 작업 공간마다 로컬에 따로 저장합니다.
- 저장 위치는 git이 worktree마다 따로 두는 내부 디렉터리입니다. 그래서 작업 공간끼리 섞이지 않고, `melog sync`로 다른 사람에게 공유되지도 않습니다.
- 한 작업 공간에서 여러 실험을 동시에 진행할 수 있는 경우는, 진행 중인 실험이 **모두 수평 구조 프로젝트에 속할 때**뿐입니다. 스냅샷이 섞이는 문제는 프로젝트와 상관없이 코드 단위에서 생기기 때문입니다. 사후 등록을 거부하는 조건도 같은 기준으로 판단합니다.
- `done`과 `abandon`은 **실험을 시작한 작업 공간에서만** 실행할 수 있습니다. 종료 스냅샷은 명령을 실행한 작업 공간의 코드를 담으므로, 다른 작업 공간에서 실행하면 엉뚱한 코드가 스냅샷으로 남기 때문입니다. 다만 작업 공간을 지워 버려서 실험을 끝낼 수 없게 되는 경우를 위해, 경고와 함께 강제로 끝내는 `--force` 옵션을 둡니다.

**이유**: 실험 기록은 모든 작업 공간과 모든 사람이 공유하므로, 실험 기록만 보고는 어느 실험이 이 작업 공간에서 진행 중인지 알 수 없습니다. 그런데 melog는 `done`이나 `abandon`의 id를 생략했을 때 이 작업 공간의 실험을 찾아야 하고, 작업 공간 규칙도 검사해야 합니다.

# melog 구현 계획

[design.md](design.md)에서 정한 설계를 어떤 순서로 구현할지 정리한 문서입니다. 단계를 마칠 때마다 체크합니다.

## 기술 선택

| 대상 | 선택 | 이유 |
|---|---|---|
| CLI | Typer | 프로젝트를 만들 때 정한 프레임워크입니다 |
| YAML | ruamel.yaml | 읽고 다시 쓸 때 원래 표기를 유지합니다. PyYAML은 `0.80`을 `0.8`로 바꾸므로, 점수의 표기를 보존한다는 규칙을 지킬 수 없습니다 |
| git | git 명령을 직접 실행 | melog는 전용 참조와 임시 인덱스 같은 저수준 기능을 주로 씁니다. 이런 기능은 GitPython이나 pygit2보다 git 명령으로 다루는 편이 단순하고 동작을 예측하기 쉬우며, 외부 의존성도 줄어듭니다 |
| 테스트 | pytest | 테스트마다 임시 git 저장소를 만들어서 실제 git 동작을 검증합니다. CLI는 Typer의 `CliRunner`로 테스트합니다 |

## 모듈 구조

`src/melog/` 아래의 모듈입니다. 표의 아래쪽 모듈일수록 git에 가깝고, 위쪽 모듈일수록 사용자에 가깝습니다.

| 모듈 | 역할 |
|---|---|
| `cli.py` | Typer 앱과 명령어 정의, 사람용 출력과 `--json` 출력 |
| `editor.py` | 편집 화면 생성(읽기 전용 항목은 주석으로 표시), 에디터 실행, 편집 결과 해석 |
| `sync.py` | 원격 저장소와의 동기화, 병합, id 충돌 해결 |
| `experiment.py` | 기록 절차(시작, 완료, 중단, 사후 등록)와 실험 기록 조회. CLI는 이 모듈을 호출하기만 합니다 |
| `record.py` | 실험 기록 모델, Markdown + frontmatter 변환, 검증(부모 존재 여부, 순환) |
| `project.py` | melog 프로젝트 설정과 개요 |
| `ids.py` | 이니셜 설정, id 발급, 순번의 숫자 정렬 |
| `workspace.py` | 작업 공간마다 로컬에 저장하는 "진행 중인 실험" 정보 |
| `snapshot.py` | 작업 트리를 건드리지 않고 스냅샷 커밋을 만들고 보존 |
| `store.py` | melog 전용 저장 공간에 파일을 읽고 쓰기. checkout 없이 git 참조 위에서 직접 다룹니다 |
| `git.py` | git 명령 실행을 감싸는 얇은 계층 |

## 구현 단계

각 단계가 끝날 때마다 실제로 쓸 수 있는 상태가 되도록 나눴습니다.

- [x] **1. 기반**: `git.py`, `store.py`, `project.py`, `melog init`, `melog project edit`(옵션 방식)
  - 이 단계 이후: melog 프로젝트를 만들고 설정할 수 있습니다.
- [x] **2. 핵심 기록**: `snapshot.py`, `record.py`, `ids.py`, `workspace.py`, `experiment.py`, `start`, `done`(`--new` 포함), `abandon`, `show`, `list`
  - 이 단계 이후: 혼자서 실험을 기록할 수 있습니다. 처음으로 실제 사용이 가능한 단계입니다.
- [x] **3. 편집**: `editor.py`, `edit`(에디터 방식과 옵션 방식), `project edit`(에디터 방식)
  - 이 단계 이후: 본문과 점수를 편하게 채우고 보강할 수 있습니다.
- [ ] **4. 코드**: `diff`, `checkout`
  - 이 단계 이후: 변경점을 확인하고 실험 코드를 재현할 수 있습니다.
- [ ] **5. 가져오기**: `import`
  - 이 단계 이후: 다른 melog 프로젝트의 실험을 가져올 수 있습니다.
- [ ] **6. 협업**: `sync.py`, `sync`
  - 이 단계 이후: 여러 사람이 실험 기록을 공유할 수 있습니다.
